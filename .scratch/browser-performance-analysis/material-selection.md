# 素材选择过程中卡死：专项判断与优化建议

日期：2026-11-16。客户描述：最新桌面版本（用户称 v2.0.18）在广告账户页选择素材，选到一半页面卡死、鼠标不动。本仓库发布分支为 `release/desktop-v0.2.18`；未读取客户 About 版本，不能认定客户端二进制完全相同。

## 判断边界

客户具体网站 DOM、操作录像、CPU/内存/GPU/磁盘、崩溃记录尚未取得；不能确诊。截图尝试本地读取及 OCR，未能可靠辨认有用配置/错误信息，不以截图推测机器配置。

- 若指针在整个 Windows 桌面也不动，任务栏、切换窗口亦失效：先按系统资源压力或 GPU/驱动异常排查，普通请求慢通常不能解释系统指针冻结。
- 若指针可移动、其他软件正常，仅素材页不响应：先按页面 renderer 主线程长任务、素材预览解码/内存增长、页面内部批量选择逻辑排查。
- 若能点击且loading旋转，只是数据不返回：仍查素材/CDN/接口的实际代理或直连路由。

这些是按症状排序的假设，不是已确认根因。广告平台为第三方页面，不能未经验证由我们直接重写素材渲染/暂停所有媒体/屏蔽业务脚本。

## 补充验证：原生 checkbox 的重复快照

真实执行现有采集脚本，测试全新 localhost 页面；使用浏览器原生 `HTMLElement.click()` 激活 checkbox（非真实鼠标或客户端到端交互）。环境为 macOS arm64、随包 headless Chrome 153.0.8010.12；报告binding为本地stub，不测Rust/网络/绘制。

每轮每场景预热50次+100组×5次激活，两轮均使用独立新页面。每页550次click，实际产生550 input和550 change，采集input计数为1100，与当前语义一致。

| 场景 | 无采集 P95，两轮 | 当前采集 P95，第1/2轮 |
|---|---:|---:|
| 50 checkbox | 约0.02ms | 0.58 / 0.56ms |
| 5000 checkbox，独立名称 | 约0.02ms | 0.66 / 0.66ms |
| 1000 checkbox，同名 | 约0.02ms | 3.40 / 3.58ms |
| 无form、约5万DOM节点 | 约0.02ms | 2.54 / 2.52ms |

直接代码原因：`desktop/src-tauri/src/cdp.rs:193-199` 的 input/change 都在 capture listener 内立即执行 `snapshotFor`，`:123-130` 选择最近form，否则扫描document。一次原生checkbox激活通常会两次扫描。如果平台控件不是原生checkbox或不发这两种事件，不能直接套用此结论。

判定：重复快照是明确可减负点，但本机实测不足解释硬冻结；低配Windows、真实图片/视频素材页面、预览内存/解码异常未验证。

## 优化优先级

### P1：受控浏览器注入层减负（优先工程候选）

1. input/change 监听保留现有事件计数；把快照收集合并到窗口内一次延后任务，按需求保留最新表单状态。不要在capture监听内重复扫描。必须限制调度间隔/最大等待，确保submit/pagehide前必要的flush，保持敏感字段过滤和字段/字节限额；不直接只采当前字段或丢弃checkbox审计内容。
2. 对无需消费的Runtime console事件，评估不启用 `Runtime.enable`。上一轮仅当前Mac Chromium验证了bindingCalled不依赖Runtime.enable，Windows随包版本及首文档/弹窗/导航/托管防护必须完整验证后才可上线。
3. 不以性能为理由关闭登录防护、改变代理路由、关闭沙箱或降低SQLite FULL持久性。

这是减小自身附加负载的优化方案，不是已修复客户故障。用户本轮要求建议，未修改产品代码。

### P1：素材预览的 GPU 与内存分支

- 在开发方/受控测试环境记录卡死前后资源曲线，区分renderer、GPU进程与桌面Rust进程。
- 在相同素材和数量、相同网络与机器下，以正常硬件加速为基准，再用测试启动配置关闭硬件视频解码做单变量对照；仅证据需要时扩展到禁GPU的诊断。禁用加速会把负载转给CPU，不作为默认优化。
- 若重复对照证明GPU分支失败，再评估可回滚兼容开关及已验证的驱动/Chromium版本，而不是全量强制禁GPU。
- 若内存持续增长/系统换页，先定位图片/视频预览、页面业务保留对象、多浏览器窗口；在平台本身支持时减少每页素材/并发预览。关闭无关窗口可临时缓解，但不代替根因修复，关闭业务窗口先确认未提交操作。

Windows CFoT的stack profiler风险已有仓库记录，可作为后续兼容实验；本客户卡死是否与其有关未验证，不先添加参数宣称修好。

### P2：活动队列

保留FULL、容量回滚和关闭排空条件下，评估增量容量统计、连接复用及受控批量写入。队列两轮实测重负载单次最大73ms，不把它作为本次鼠标冻结的确定原因。

## 验收

1. 客户操作量/素材类型先确认，使用相同操作两轮复现；覆盖当前会卡死数量并超出该数量，记录是否完成，不杜撰统一阈值。
2. 同时观察页面交互延迟、长任务、CPU/GPU、内存和磁盘趋势，确认是否出现系统级卡顿。
3. 优化前后对照只改变一个因素；功能完成和资源证据都成立才宣称改善。
4. checkbox/input/change计数、快照脱敏和限额、submit/pagehide、首文档/弹窗、托管失效、防护行为回归通过；不静默改变审计口径。
5. 保留未提交选择，不自动重启/清理profile；新兼容模式可回滚。
