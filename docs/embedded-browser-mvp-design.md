# HTTP 代理内嵌浏览器 MVP 开发文档

> 历史设计稿：本文记录最初“用户手填单条代理”的 v0.1 方案，已经被当前集中管理实现取代，不能作为部署或验收依据。当前实现以根目录 [README.md](../README.md)、[docs/backend.md](backend.md) 和代码为准：Web 仅管理员，代理/平台由管理员分配，Rust 桌面用户登录后同步，代理口令仅保留在 Rust 会话内存。

文档版本：v0.1  
当前阶段：只实现 HTTP 代理配置和内嵌浏览器  
技术方向：Rust + Tauri 2

## 1. 本阶段目标

开发一个最小可用的桌面应用：

1. 用户填写 HTTP 代理的 IP、端口、账号和密码。
2. 应用测试代理是否可以正常连接。
3. 应用打开一个内嵌浏览器。
4. 内嵌浏览器的 HTTP 和 HTTPS 请求都经过用户配置的 HTTP 代理。
5. 代理不可用时，浏览器请求失败，不能自动改用本机网络。
6. 界面显示浏览器通过代理访问时的实际出口 IP。

本阶段不实现广告业务逻辑，也不实现 API 自动化。

## 2. 当前功能范围

### 2.1 代理配置

配置页面包含以下字段：

| 字段 | 必填 | 示例 | 说明 |
|---|---:|---|---|
| 代理 IP | 是 | 203.0.113.10 | 代理服务器地址，也允许填写域名 |
| 代理端口 | 是 | 8080 | 取值范围 1～65535 |
| 代理账号 | 是 | proxy_user | 上游代理认证账号 |
| 代理密码 | 是 | ******** | 输入框默认隐藏 |
| 启动网址 | 否 | https://www.oceanengine.com/ | 浏览器启动后的首个地址 |

页面提供三个操作：

- 测试代理
- 保存配置
- 打开浏览器

代理 IP、端口和账号可以保存在应用配置中。代理密码不写入明文 JSON、日志或 URL，使用 Windows Credential Manager 或 macOS Keychain 保存。

### 2.2 内嵌浏览器

浏览器需要支持：

- HTTP 和 HTTPS 网站。
- 地址栏、导航、后退、前进、刷新和停止加载。
- 网页正常输入、点击、登录和跳转。
- Cookie 和登录状态持久化。
- 显示当前代理状态和实际出口 IP。
- 关闭后再次打开，继续使用已保存的代理配置。

浏览器中的所有操作由用户人工完成。本阶段不注入业务脚本，不自动点击页面。

## 3. 明确不做

以下内容全部移出当前版本：

- 多广告账户管理和多 profile。
- 自动改价、自动调预算、自动启停和自动报表。
- 巨量 Marketing API。
- DOM 自动点击、键盘模拟和页面脚本注入。
- 验证码识别、MFA 自动处理和指纹伪装。
- 规则引擎、任务队列、审批和业务审计。
- 公司 Gateway、远程浏览器和集中管理后台。
- SOCKS5、PAC 和系统全局代理。

这些功能后续单独立项，不作为本 MVP 的前置依赖。

## 4. 推荐实现结构

    Tauri 管理界面
        ├── IP / 端口 / 账号 / 密码
        ├── 测试代理 / 保存 / 打开浏览器
        └── 代理状态 / 出口 IP
                    │
                    ▼
    Rust 本地 HTTP 代理适配器
        ├── 监听 127.0.0.1 的随机端口
        ├── 连接用户配置的上游代理
        ├── 处理代理账号密码认证
        └── 禁止任何直连兜底
                    │
                    ▼
    内嵌 WebView
        └── 固定使用 http://127.0.0.1:本地端口
                    │
                    ▼
    用户配置的 HTTP 代理 → 目标网站

不建议把 账号:密码@IP:端口 直接拼进 WebView 代理 URL。不同 WebView 对代理认证的处理不一致，密码也可能进入日志、错误信息或启动参数。

推荐由 Rust 启动一个只监听 127.0.0.1 的本地代理适配器：

1. WebView 只连接本地适配器。
2. 适配器使用用户填写的账号和密码连接上游 HTTP 代理。
3. 普通 HTTP 请求通过上游代理转发。
4. HTTPS 请求通过上游代理的 CONNECT 隧道转发。
5. 上游代理失败时返回错误，绝不直接连接目标网站。

## 5. 代理连接流程

### 5.1 测试代理

用户点击“测试代理”后：

1. 校验 IP、端口、账号和密码是否完整。
2. Rust 连接指定的代理 IP 和端口。
3. 使用代理账号密码发起带认证的 HTTP CONNECT 请求。
4. 通过代理访问 HTTPS 出口检测地址。
5. 返回测试结果和实际出口 IP。

成功示例：

    代理连接成功
    代理服务器：203.0.113.10:8080
    实际出口 IP：198.51.100.25
    检测时间：2026-08-26 10:30:00

代理服务器 IP 和实际出口 IP 不一定相同，因此不能把二者简单比较为必须相等。

失败时显示明确原因：

- 无法连接代理服务器。
- 连接超时。
- 代理账号或密码错误（HTTP 407）。
- 代理拒绝 CONNECT。
- 无法访问出口检测地址。

### 5.2 打开浏览器

用户点击“打开浏览器”后：

1. 再次检查代理配置。
2. 启动本地 HTTP 代理适配器。
3. 把 WebView 的代理设置为本地适配器地址。
4. 创建新的 WebView 浏览器环境。
5. 由 WebView 自身访问出口检测地址。
6. 检测成功后显示出口 IP，并打开启动网址。
7. 检测失败则关闭 WebView、停止适配器并提示错误。

不能先创建无代理 WebView，再在运行中修改代理。代理必须在创建浏览器环境之前确定。

### 5.3 修改代理

当前版本不支持运行中热切换。修改代理时必须：

1. 关闭当前 WebView。
2. 停止旧的本地代理适配器。
3. 释放旧浏览器网络环境。
4. 测试新的上游代理。
5. 重新启动适配器并创建 WebView。

## 6. 如何确认浏览器确实使用代理

只在 Rust 后端测试代理不够，因为这不能证明 WebView 的请求也经过代理。

### 6.1 WebView 自身出口验证

WebView 创建后，首先由 WebView 自己访问出口 IP 检测地址。应用读取该页面返回的出口 IP，成功后才允许进入普通网页。

出口检测地址做成配置项。开发阶段可使用公开 HTTPS 服务，正式使用建议改为公司自己的简单 HTTPS 接口。

### 6.2 连接链路检查

本地适配器只记录不含敏感信息的连接事件：

    WebView → 127.0.0.1:本地端口
    本地适配器 → 配置的代理 IP:端口
    上游代理 → 目标网站

日志只保留目标域名、连接结果和时间，不记录代理密码、Cookie、请求正文或完整查询参数。

### 6.3 禁止直连兜底

- WebView 只配置一个固定的本地代理地址。
- 适配器只允许连接用户填写的代理 IP 和端口。
- 适配器代码不得包含“代理失败后直接请求目标地址”的路径。
- 适配器退出或上游代理断开后，页面新请求必须失败。
- 界面不提供“代理失败时继续打开”的按钮。

### 6.4 抓包验收

开发验收阶段使用系统网络监控或抓包工具确认：

- WebView 进程只连接本机代理适配器。
- 本地适配器只连接配置的代理 IP 和端口。
- WebView 和适配器没有直接连接目标网站 IP。

## 7. 浏览器状态

    未配置 → 正在测试 → 可以打开 → 浏览器运行中
                  └──────────→ 代理错误
    浏览器运行中 ─────────────→ 代理断开

| 状态 | 行为 |
|---|---|
| 未配置 | 禁止打开浏览器 |
| 正在测试 | 禁止重复提交 |
| 可以打开 | 允许创建 WebView |
| 浏览器运行中 | 显示代理地址和出口 IP |
| 代理错误/断开 | 页面请求失败，禁止直连，可重新测试 |

## 9. 配置数据

非敏感配置可以使用本地 JSON 或 SQLite：

    {
      "proxy": {
        "host": "203.0.113.10",
        "port": 8080,
        "username": "proxy_user",
        "password_key": "vestus.http_proxy.default"
      },
      "start_url": "https://www.oceanengine.com/"
    }

password_key 只是系统密钥链中的引用，不是实际密码。本阶段只保存一套代理配置，不开发代理列表和多账号映射。

## 10. 平台实现说明

### Windows

使用 WebView2。创建浏览器环境时传入固定代理配置，并使用独立 user-data 目录。代理发生变化后销毁旧环境并重新创建。

### macOS

使用 WKWebView。macOS 对 WebView 独立 HTTP 代理的支持必须进行实机验证。如果当前 Tauri/Wry 版本不能可靠设置固定代理，则该平台暂不开放浏览器功能，不能改用系统直连作为降级方案。

建议先完成 Windows 版本，再按相同验收标准验证 macOS 14+。

## 11. MVP 验收标准

满足以下全部条件才算本阶段完成：

1. 可以填写并保存代理 IP、端口、账号和密码。
2. 正确配置能够测试成功，并显示实际出口 IP。
3. 错误账号或密码能够识别为认证失败，不能打开浏览器。
4. 内嵌浏览器能够正常打开 HTTP 和 HTTPS 网站。
5. 出口检测请求由 WebView 自身发出，而不是只由 Rust 后端发出。
6. WebView 展示的出口 IP 是通过配置代理访问得到的出口。
7. 上游代理停止后，页面新请求失败，不能使用本机网络继续访问。
8. 抓包确认 WebView 没有直接连接目标网站。
9. 修改代理后必须关闭并重建浏览器环境。
10. 代理密码不会出现在配置文件、日志、代理 URL 或错误提示中。
11. 应用内没有自动点击、页面脚本注入和广告业务 API。

## 12. 开发顺序

1. 创建 Tauri 2 基础项目和代理配置页面。
2. 实现配置校验和系统密钥链存储。
3. 实现 Rust 本地 HTTP 代理适配器及上游认证。
4. 实现代理测试和出口 IP 获取。
5. 创建使用固定本地代理的内嵌 WebView。
6. 实现由 WebView 发起的出口验证。
7. 实现地址栏、前进、后退、刷新和状态显示。
8. 完成错误密码、代理断开和禁止直连测试。
9. 完成 Windows 打包和验收。
10. 验证 macOS 14+ 的代理配置能力。

- Rust 本地代理适配器。
