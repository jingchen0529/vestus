# 桌面端版本说明与发版规则

每次打包先说明，再确认，再提交。版本说明与代码一起保存，GitHub Release 直接使用该版本文件，不再只展示通用下载模板。

## 固定顺序

1. **核对范围**：选择版本号，对照上一发布 tag 与本次待发布代码，确认本版实际变化、目标环境与 API 地址。不要把旧功能重复写成新增，也不要把尚未执行的验证写成已通过。
2. **写说明并展示**：创建 `docs/releases/desktop-v<version>.md`，使用下方六章模板；在对话中先完整展示给用户。
3. **等待确认**：用户明确确认这份说明后，才提交发版相关代码和说明。仅说“打包”不能代替确认尚未展示的说明。版本、环境或实质内容变化后，重新展示并确认。
4. **本地检查**：从仓库根目录运行 `node desktop/scripts/check-release-notes.mjs <version>`。按项目门禁运行测试，将实际结果补入说明；未验证的项目明确标注。
5. **提交与打包**：提交已确认的代码和文档，再按用户授权推送 `desktop-v<version>` 标签，或手动运行 `Release`。构建提交必须包含对应说明文件，不能只留在未提交的工作区。
6. **核验结果**：构建结束后查看实际结论与资产，确认 GitHub Release 正文使用该文件。失败、跳过或尚未完成的项目如实报告。

普通提交请求不自动触发发版；发版不自动授权服务器部署。不得为补说明而移动已有 tag、重建历史包或修改其他环境。

## 文件格式与校验

- 文件名固定为 `desktop-v<version>.md`，版本号只接受 `x.y.z` 数字格式，与 `desktop/scripts/stamp-version.mjs` 一致。
- 一级标题必须为 `# Vestus desktop-v<version> 版本说明`，且只能有一个一级标题。
- 必须包含下面六个二级标题及实际内容；没有迁移或额外限制时也写清楚，不留空。
- 「发布信息」必须各有一条 `- 目标环境：...` 和 `- API 地址：...`。地址使用完整 HTTP(S) URL，不含用户名、密码、查询参数或片段。
- 正式标签构建仍要求 HTTPS；非标签手动测试构建沿用现有 HTTP 显式允许规则。本检查只验证文档中的地址格式，执行者仍须确认它与实际构建输入/Secret 一致，不能凭 `gh secret list` 推断 Secret 的值。
- `待填写`、`待补充`、`请填写`、`TODO`、`TBD`、`FIXME` 等模板占位内容会被拒绝。允许明确写“未验证”，不要求为了过检查虚报结果。
- 校验器不理解业务真实性，也不能证明对话中的人工确认；`AGENTS.md` 负责约束确认顺序。

### 模板（不能原样用于打包）

将下列内容复制到对应版本文件，替换版本号和所有占位内容。不要把真实密码、Cookie、访问令牌或数据库连接凭据写入说明。

```markdown
# Vestus desktop-v0.2.13 版本说明

## 发布信息
- 目标环境：待填写（dev 测试环境 / 正式环境等）
- API 地址：待填写
- 对比版本：待填写

## 本次更新
- 待填写：本版新增、修复和行为变化；基于实际代码，而不是仅照抄提交标题。

## 安装与升级
- 待填写：Windows x86_64、macOS Apple Silicon / Intel、Linux x86_64 的安装包和安装方式。
- 待填写：覆盖安装/退出旧客户端的要求，以及 macOS 签名公证、Linux 登录持久化等适用限制。

## 后端配套
- 待填写：最低配套后端、接口变化、数据库迁移与升级顺序；没有新增要求也写清楚。

## 验证结果
- 待填写：实际执行的测试和结果；未完成项目明确写“未验证”。推 tag 前不能声称本次四平台发布已成功。

## 已知限制
- 待填写：未验收场景、兼容性变化、手工操作和其他注意事项。
```

用户指南、下载入口、比较链接等可放在相应章节或另加二级章节。文档链接建议指向本次 tag/提交，不指向持续变化的 `main`。

## 自动化行为

`Release` 先运行不需要 npm 依赖、Rust 或 Chromium 的 `preflight`，校验通过才启动四平台矩阵；缺文件、空内容、版本不符或缺章节都会提前失败。

- **tag 推送**：从 `desktop-v<version>` 取版本号，校验同一提交的说明后构建；所有构建成功后，发布任务以 `body_path` 使用该说明。
- **手动构建**：在 `Release` 表单填写 `version`（如 `0.2.13`），所选提交也必须包含该说明。若选择的是 `desktop-v*` tag，输入版本必须与 tag 一致。产物版本和文件名使用这个版本号，但只上传 Actions Artifacts，不创建 GitHub Release。
- `preflight`、四平台构建和发布均检出同一 `github.sha`，不从可变分支另取说明。
- 此规则只影响包含新工作流的后续提交，旧 tag 的历史工作流不会被改写。不要用重打历史标签的方式补规则。

手动在本机复现版本化安装包也须先展示并确认说明、运行本地校验；CI 前置检查不拦截任意终端里直接执行的构建命令。

## 本地验证

```sh
node --test desktop/scripts/check-release-notes.test.mjs
node desktop/scripts/check-release-notes.mjs 0.2.13
npm --prefix desktop test
npm --prefix desktop run build
npm --prefix desktop run check:surfaces
```

示例版本 `0.2.13` 的说明文件未准备好时，第二条命令失败是预期行为，不要为恢复绿灯提交空白模板。
