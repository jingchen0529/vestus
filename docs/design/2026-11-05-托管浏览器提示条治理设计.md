# 托管浏览器 Chrome for Testing 提示条治理设计

> 状态：设计稿，待评审
>
> 关联 issue：[.scratch/managed-chromium-infobar/issues/01-infobar-covers-ark-menu-top.md](../../.scratch/managed-chromium-infobar/issues/01-infobar-covers-ark-menu-top.md)
>
> 现象：客户机（Windows）上托管启动的方舟窗口，地址栏下方常驻一条
> 「Chrome 测试版 v153.0.8010.12 仅适用于自动测试……」提示条，页面视口被压掉约
> 40px，方舟顶部菜单下移，现场截图疑似出现顶部空带。

## 0. 结论先行

| 方案 | 有效性 | 背书 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| ① 启动参数加 `--disable-infobars` | 对 CFoT + 持久化 profile 有效，对 Chromium/正式版 Chrome/Edge 被忽略 | Playwright main 分支现役做法 | 极低，只影响 infobar UI | **采用** |
| ② 启动参数加 `--test-type=gpu` | 社区多人验证，裸 `--test-type` 无效 | 无官方承诺，未来版本可能失效 | 抑制面更大（一类测试警告） | 备选，①失效时启用 |
| ③ 打包换正式版 Chrome/Edge 渠道 | 彻底无此条，也无 CFoT 特征 | — | Chrome 重分发条款、打包体积；Edge 在 Windows 系统自带 | 长期项，单独决策 |
| ④ 换 Chromium 构建（非 CFoT） | 无此条（Puppeteer 官方建议） | Puppeteer 维护者 | 获取与更新渠道要重建 | 并入③一起决策 |
| ⑤ 不去条，仅窗口几何补偿 ~40px | 治标 | — | 客户仍看到「仅适用于自动测试」字样 | 不采用，仅作①②都失效时的兜底 |

推荐先落①：一行启动参数 + 一条测试断言，提示条消失后视口少 ~40px、
「菜单顶部被挡」的主诉随之解除。

## 1. 问题回顾

### 1.1 定性

提示条不是网页内容、不是 Vestus 注入的 UI，而是 **Chrome for Testing（CFoT）构建自带的
内置 infobar**，由浏览器窗口自身渲染，位于地址栏和网页视口之间，页面 JS/CSS 不可达。
桌面端打包的浏览器正是 Playwright 下载的 CFoT 构建
（[desktop/scripts/chromium-resource.mjs](../../desktop/scripts/chromium-resource.mjs) 注释
明确 macOS 下 `.app` 名为 "Google Chrome for Testing.app"）。

### 1.2 机制

- infobar 不是盖在页面上的浮层，而是把网页视口整体下压。桌面端用
  `--window-position` / `--window-size` 显式下发外框几何
  （[desktop/src-tauri/src/browser.rs:1167](../../desktop/src-tauri/src/browser.rs:1167)），
  外框高度固定，tab 条 + 地址栏 + infobar 都从同一高度里扣，
  **页面可用高度直接少约 40px（随 DPI 缩放）**。
- CFoT 这条提示从窗口创建第一帧就常驻，视口「从头就矮一截」，布局稳定，不会中途跳。
- 托管链路 `about:blank → Rust 注 Cookie → 导航到业务 URL` 中 CDP resize 与页面首帧
  存在竞态的可能性，是「菜单空带」的候选解释之一，实测环节区分（见 4.2）。

### 1.3 影响面

| 影响点 | 程度 |
| --- | --- |
| 页面视口高度少 ~40px，方舟顶部菜单下移/疑似错位 | 确定存在，本设计主诉 |
| 客户看到「仅适用于自动测试」字样，暴露自动化痕迹 | 确定存在，观感/风控观感问题 |
| CDP 采集、Cookie 注入等功能 | 不受影响（CDP 截图只看网页视口，拍不到浏览器 chrome） |
| 服务端登录 Worker | 不受影响：`app/services/managed_platforms.py:331` 以 `headless=True` 启动，无 UI 即无提示条 |

## 2. 方案① 设计：`chromium_arguments()` 追加 `--disable-infobars`

### 2.1 依据

Playwright 在 [chromiumSwitches.ts](https://github.com/microsoft/playwright/blob/main/packages/playwright-core/src/server/chromium/chromiumSwitches.ts)
中的注释原文：

> This disables Chrome for Testing infobar that is visible in the persistent context.
> The switch is ignored everywhere else, including Chromium/Chrome/Edge.

我们的启动形态（chrome.exe + `--user-data-dir` 持久化 profile）正是 persistent
context，与 Playwright 生效条件一致。注意区分：`--disable-infobars` 去不掉**正式版
Chrome 的「正受到自动测试软件的控制」提示条**（~M65 已失效，playwright#36238 实证），
那是另一条提示，本设计不涉及。

### 2.2 改动点

**改动 1：启动参数**
[desktop/src-tauri/src/browser.rs:1146](../../desktop/src-tauri/src/browser.rs:1146) 的
`args.extend(vec![...])` 块内追加一项，注释说明来龙去脉（为什么是它：Playwright
persistent context 背书、仅 CFoT 生效、被其他构建忽略）：

```rust
// Chrome for Testing 构建会在持久化 profile 的窗口里常驻一条「仅适用于自动测试」
// 的 infobar，吃掉页面视口约 40px（issue: managed-chromium-infobar/01）。
// --disable-infobars 恰好只对这条提示生效；Playwright 对 persistent context
// 用的就是它。该参数被 Chromium/正式版 Chrome/Edge 忽略，不构成副作用面。
OsString::from("--disable-infobars"),
```

位置约束：**起始网址必须仍是最后一个参数**（现有测试
`chromium_arguments_use_only_loopback_proxy_and_the_given_profile`
在 [browser.rs:1188](../../desktop/src-tauri/src/browser.rs:1188) 断言
`rendered.last() == target_url`），新参数放进 `args.extend` 块即可自然满足。

**改动 2：测试断言**
在 `chromium_arguments_use_only_loopback_proxy_and_the_given_profile` 中补：

```rust
// CFoT 提示条必须压掉：否则窗口顶部常驻一条「仅适用于自动测试」，页面视口少 ~40px。
assert!(rendered.contains(&"--disable-infobars".into()));
```

### 2.3 明确不动的部分

- **`WindowGeometry` / `FALLBACK_WINDOW` 不动**：提示条去掉后视口自然恢复，
  不需要几何补偿（方案⑤不采用）。
- **服务端 Playwright Worker 不动**：headless 启动，无提示条可言。
- **`chromium-resource.mjs` / 打包布局不动**：仍用 Playwright 的 CFoT 构建，
  换渠道是方案③的独立决策，不混入本次改动。

### 2.4 附带观察项（不在本票内实现）

Playwright 同文件还带 `--disable-stack-profiler`，注释：CFoT 启用的栈采样分析器
在 Windows 上展开主线程时会崩溃。客户机恰是 Windows，建议起独立小票验证
我们是否踩过这个坑，再决定是否加入；不与方案①捆绑。

## 3. 备选与长期项

- **备选② `--test-type=gpu`**：仅当实测证明 v153 上 `--disable-infobars` 无效时启用。
  语义是「抑制测试类 UI 警告」，抑制面比单条 infobar 大，且非官方承诺。
- **长期项③/④ 换渠道**：彻底消除提示条和 CFoT 特征，对风控观感是加分项，但需要
  单独评估：Google Chrome 的重分发条款（当前打包 CFoT 正是为了避开它）、Edge 在
  Windows 上系统自带（Playwright 社区的 `channel: 'msedge'` 是常见替代）、打包体积
  与更新机制。建议评审通过方案①后，另行立项（必要时走 ADR）。

## 4. 实测与验收

### 4.1 自动化

```bash
cargo test --manifest-path desktop/src-tauri/Cargo.toml --all-targets
python3 -m pytest -q   # 确认服务端链路无回归
```

### 4.2 手工验收清单（Windows 客户机 + macOS dev 各一轮）

1. 启动方舟托管页，确认地址栏与页面之间**无提示条**，窗口顶部直接是页面内容。
2. 视口量化：CDP 里读 `window.innerHeight` 与 `document.documentElement.clientHeight`，
   加参数前后对比应差约 40px（infobar 高度，随 DPI 缩放浮动）。
3. 方舟顶部菜单完整可见；若仍有空带，用 CDP 读顶部菜单元素
   `getBoundingClientRect()` 区分「视口偏移」与「渲染异常」（后者另开 issue）。
4. 既有行为回归：代理开/关、沙箱开/关（`--no-sandbox` 逃生阀）、
   `--hide-crash-restore-bubble`、占用检测认进程不受影响（参数首项仍是
   user-data-dir 参数）。
5. 版本矩阵：当前 CFoT v153 实测通过即收口；**CFoT/Playwright 升级后复测此项**，
   把「提示条仍被压住」列入升级检查单（该参数是 Playwright 现役做法但非 Chromium
   官方承诺，行为可能随版本变化）。

### 4.3 失败预案

若 v153 上 `--disable-infobars` 无效：切② `--test-type=gpu` 实测；仍无效则临时走
⑤ 窗口几何补偿兜底，并把方案③换渠道的决策提前。

## 5. 风险与回滚

- 风险：极低。参数只影响浏览器自身 infobar UI，对非 CFoT 构建被忽略，
  不触碰沙箱/代理/调试端口等已有约束。
- 回滚：删一行参数即可，无数据或 profile 兼容性问题。

## 6. 非目标

- 不解决 CFoT 构建的其它自动化痕迹（UA、`navigator.userAgentData.brands` 等可被
  站点侧检测的面），那是风控议题，另立。
- 不处理服务端 Worker 的浏览器选择（headless 场景无此问题）。
- 不在本设计内决定是否更换打包渠道（方案③），只列出决策所需的约束。
