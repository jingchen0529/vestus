# Vestus 整体架构设计

> 日期:2026-11-04
> 范围:后端(FastAPI)、管理端(React)、桌面端(Tauri)三端的模块划分、缝的位置与演进方向。
> 方法论:深模块设计(deep module)——用小接口藏大实现,让调用方以最少的认知换取最多的行为,
> 让维护者把变更、缺陷、验证集中在同一处。

---

## 0. 词汇表

| 术语 | 含义 |
| --- | --- |
| **模块 Module** | 有接口和实现的东西,尺度不限:一个函数、一个类、一个包、一段跨端切片 |
| **接口 Interface** | 调用方正确使用它必须知道的一切:类型、不变量、顺序约束、错误模式、所需配置 |
| **实现 Implementation** | 接口背后的代码主体 |
| **深度 Depth** | 接口的杠杆率:每学一分接口,能驱动多少行为。深 = 小接口大实现 |
| **缝 Seam** | 接口所在的位置;不改此处代码就能替换行为的地方 |
| **适配器 Adapter** | 在缝上满足接口的具体实现。一条缝有两个适配器才是真缝,只有一个是假想缝 |
| **杠杆 Leverage / 局部性 Locality** | 深度给调用方/维护方的回报 |

判断一个模块是否该存在,用**删除测试**:删掉它,如果复杂度凭空消失,它是传声筒;如果复杂度在 N 个调用点重新冒出来,它在挣自己的饭钱。

## 1. 系统上下文

```
管理员 ──▶ 管理端 Web (React)  ─┐
                                ├──▶ 后端 API (FastAPI) ──▶ MySQL / 上传目录
桌面用户 ──▶ 桌面端 (Tauri)    ─┘         │
   │                                     │
   └─ 随包 Chromium ──▶ 巨量引擎等广告平台(经上游代理或直连)
```

外部依赖:广告平台 Web(被操作对象)、上游代理线路(出站)、随包 Chromium(被驱动对象)。
后端不直接触碰这三者;桌面端是唯一的三者交汇点——这是整张架构图里最重要的职责划分。

---

## 2. 容器与职责

| 容器 | 技术 | 对外接口 | 深度来源 |
| --- | --- | --- | --- |
| 后端 | FastAPI + SQLAlchemy + MySQL | HTTP + 统一响应信封 | 信封/分层契约把 84 个文件的复杂度压在 `create_app()` 一个组合根后面 |
| 管理端 | React + shadcn-ui | 人机界面 | `api-client.ts` 单一 HTTP 缝 |
| 桌面端壳 | React (desktop/src) | 人机界面 | `tauriBridge.ts` 单一 IPC 缝,fail closed |
| 桌面端内核 | Rust (desktop/src-tauri) | Tauri command 面 | 16.8k 行 Rust 藏在约 30 个 command 后面 |

**职责铁律**:代理分流、Chromium 生命周期、活动采集、凭据保管只存在于 Rust 内核;
Web 管理端与桌面壳永远不模拟这些能力(`check-surface-boundaries.mjs` 用静态检查强制这一点)。

## 3. 后端:MVP 分层即缝的顺序

```
main ──▶ api ──────▶ services ──────▶ repositories ──▶ db
  \        \             │
   \        └─▶ schemas ◀┘        ← 共享 DTO,不在垂直链上
    └──▶ core(横切,自身零项目内依赖)
```

六条 import-linter 契约(见 `.importlinter`)把这条顺序变成 CI 里可执行的断言,
而不是文档里的愿望。分层不是目的,**每层是一条缝**,缝上有明确的替换纪律:

| 层 | 缝上允许出现的 | 禁止出现的 |
| --- | --- | --- |
| `app/api` | HTTP 语义(状态码、cookie、依赖注入) | SQL、业务规则 |
| `app/services` | 业务规则、事务编排、ORM→DTO(经 `services/serializers`) | `fastapi`/`starlette` |
| `app/repositories` | 查询与持久化,返回 ORM 实体 | DTO、业务判断 |
| `app/schemas` | 纯 Pydantic 数据契约 | 任何项目内模块(`core` 工具与 `db.base` 底层助手除外) |

### 3.1 关键深模块

| 模块 | 接口(调用方需知的全部) | 实现里藏着的 | 深度论证 |
| --- | --- | --- | --- |
| `app.main.create_app` | 无参工厂,返回就绪的 ASGI 应用 | 配置校验、DB 打开、中间件、路由装配、错误族→信封映射、OpenAPI 包裹 | 全部装配知识集中一处;测试逐个造独立实例,行为不漏进全局 |
| `app.api.envelope` | `envelope_response(payload, code)`,`ApiCode` 枚举 | 成功/失败包裹、OpenAPI schema 注入、错误契约 | 17 个 router 不必各自定义响应形状;测试经同一信封断言(`tests/envelope.py` 是它的测试面镜像) |
| `app.services.*`(按域) | 每域若干动词函数 `(db, ...) -> dict` | 事务边界、审计、serializer 调用、跨 repo 协调 | router 学一个函数名就得到完整业务行为;HTTP 语义被挡在缝外 |
| `app.services.managed_ark_login` + `managed_recovery` | 「为绑定执行登录」「恢复失效会话」两个动词 | 方舟平台前端校验识别、凭据版本、重试等待、会话状态机 | 平台特异性全部藏在实现里;上层只见状态字段 |
| `app.services.serializers` | `user_dict`/`platform_dict`/… 纯函数 | ORM→JSON 的全部形状知识(含脱敏、内联安全判断) | 响应形状只有一份真源;desktop/admin 两端共用 |
| `app.db.session.Database` | `session()` 上下文、`initialize`、`ping` | 引擎生命周期、SQLite/MySQL 变体、事件挂接 | 测试用 `sqlite:///` 即换后端——这也是一条真实存在的缝(两个适配器:MySQL 生产 / SQLite 测试) |
| `app.core.device` | `normalize_device_id` | 设备指纹归一规则 | 一处修正,desktop 上报与后端校验同时生效 |

### 3.2 已识别的浅模块风险

- `app/api/login.py`、`deps.py`、`envelope.py`、`responses.py` 四个 api 层共享助手各司其职,
  目前不算浅;但若 `responses.py` 与 `envelope.py` 的职责继续重叠,应合并成一个「响应契约」模块。
- `tests/services/` 目前是空占位——services 作为最深的业务层,恰恰最缺不启 HTTP 的单测面。
  补测试时经 service 函数直接断言,不许穿透到 repository。

## 4. 桌面端:一条 IPC 缝,五个内核深模块

```
desktop/src (React 壳)
   │  tauriBridge.ts —— 唯一 IPC 缝,能力缺失时 fail closed
   ▼
commands.rs —— 唯一 command 面(约 30 个 #[tauri::command])
   │
   ├─ auth.rs        桌面认证:登录、令牌保管、自动登录、版本协商
   ├─ browser.rs     Chromium 进程树、生命周期、持久会话
   ├─ profile.rs     持久 profile 管理(2.2k 行,最大的模块)
   ├─ adapter.rs ┐
   ├─ bypass.rs  ├─ 本地代理适配器:按直连清单分流到上游代理或直连
   ├─ upstream.rs┘
   ├─ cdp.rs / managed_cdp.rs   DevTools 协议活动采集(普通/托管两态)
   ├─ activity.rs + activity_outbox.rs   聚合 → outbox 批量上报(断网续传)
   └─ device.rs / probe.rs / config.rs / state.rs / httpio.rs
```

### 4.1 关键深模块

| 模块 | 接口 | 藏着的 | 深度论证 |
| --- | --- | --- | --- |
| `commands.rs` + `tauriBridge.ts` | 约 30 个 command,壳侧对应类型化的函数 | 全部内核能力 | 壳学 30 个函数名得到 16.8k 行行为;`check-surface-boundaries.mjs` 在 CI 前静态验证壳不越缝 |
| `browser.rs` | 「打开某平台」「关闭会话」级别的命令 | 进程树管理、崩溃恢复、持久化测试(`mod persistence_tests`) | Chromium 生命周期知识不外泄 |
| `adapter.rs` 族 | 「这段流量该怎么出站」由清单决定 | 直连域名匹配、上游代理协议、分流规则 | 网络拓扑对壳完全不可见 |
| `cdp.rs` / `managed_cdp.rs` | 「采集页面活动」 | CDP 会话、事件去重、托管态登录检测 | 采集协议演化不改动上报格式 |
| `activity_outbox.rs` | 「提交一批活动」 | 本地队列、重试、断网续传 | 上报可靠性策略集中一处,调用方只有成功/失败 |

**缝的纪律**:壳与内核之间只有 `tauriBridge.ts` 一条路,且「缺能力必须报错而不是假装成功」
(bridge 注释原文 fail closed)。这是全仓库最强的一条缝纪律,值得作为范例保持。

## 5. 管理端:一个 HTTP 缝 + 按域组件

- `web/src/lib/api-client.ts`:唯一 HTTP 出口,所有请求经它走信封解包——对应后端的 `envelope` 缝,
  两端契约靠 `web/src/types/*.py`→`*.ts` 的手写镜像维持。
- `components/<域>/`:activity、admins、managed-platforms、… 每域 view + table + dialog,
  与后端 router 一一对应;跨域状态只经 `hooks/use-auth` 等少量 context。
- ~~浅模块预警~~(**2026-11-04 调查后撤回**):原判断认为两端 `components/ui/` 是「假想缝的复制」,
  实际逐文件 diff 证明它们是**两种有意的适配器**——desktop 是触感优先的登录壳
  (`rounded-lg`、`ring-2 + ring-offset`、hover 阴影、按压缩放),web 是信息密度优先的管控台
  (`rounded-md`、`ring-1`、`select-none`、`Loader2`);button 82/62 行里 56 行不同,switch 57 行全异。
  现在抽 `packages/ui` 只会得到「胖接口藏两个瘦实现」的浅抽象。撤回该建议;
  仅当两端某组件重新收敛为逐字相同时,再对那一个组件抽包。

## 6. 三条关键数据流(缝的串联)

1. **登录与配置下发**
   桌面壳 `authService` → `POST /api/user/login`(bearer)→ `GET /api/desktop/config`
   → Rust `device.rs` 提供设备指纹 → services/desktop.py 按 `bound_admin_id` 裁剪可见面。
   **缝价值**:桌面端永远不知道其他用户的存在。

2. **打开平台浏览器**
   壳 → `tauriBridge` → `commands.rs` → `browser.rs` 起随包 Chromium → `adapter.rs` 按清单分流
   → `profile.rs` 恢复持久 profile → `managed_cdp.rs` 检测托管登录态。
   **缝价值**:壳只发一个命令,五模块协作不可见。

3. **活动上报**
   `cdp.rs` 采集 → `activity.rs` 聚合 → `activity_outbox.rs` 排队 → `POST /api/user/browser-activity/v2`
   (批量、幂等 receipt)→ `services/browser_activity.py` → `logs/audit`。
   **缝价值**:两端各自的 outbox/信封保证「至多一次丢,不重复入库」。

| # | 方向 | 依据 | 动作 |
| --- | --- | --- | --- |

## 8. 不做什么(同等重要)

- 不引入微服务:三端一体、单机部署(systemd + nginx),拆分只增加缝、不增加杠杆。
- 不在后端引入事件总线/消息队列:桌面端 `activity_outbox` 已经承担了可靠投递,服务端无需第二个 outbox。
- 不把 Rust 内核的模块拆得更碎:`profile.rs` 2.2k 行是深模块的常态(小接口大实现),
  拆分只在接口膨胀时发生(见演进 #2),不按行数机械拆。
