# 巨量方舟托管登录设计

> 状态：本地阶段 A 已实现，真实方舟账号验收中
>
> 目标：客户在 Vestus 桌面端点击“巨量/方舟”后，浏览器直接进入已登录状态；客户不需要输入方舟账号密码，也不进入方舟登录页。

当前分支已经落地本地托管链路：超级管理员在桌面用户行内保存方舟账号密码或 Cookie，服务端验证后签发一次性会话，Rust 启动独立 Chromium profile，先注入 Cookie 再导航。账号、密码和 Cookie 明文保存在后台，只有超级管理员管理接口可读取，普通管理员和桌面用户不可见。服务端登录目前使用通用 Playwright 表单识别，方舟出现验证码、MFA、SSO 或页面结构不匹配时会明确返回人工处理，不绕过风控。

## 本地测试步骤

先准备环境并迁移数据库：

```bash
python3 -m pip install -r requirements.txt
cp .env.example .env
```

在 `.env` 中至少填写稳定的 `VESTUS_SECRET_KEY`、`VESTUS_PLATFORM_SECRET_KEY`、数据库地址和首个管理员密码。要测试“后台输入账号密码、服务端自动取得 Cookie”，还要设置 `VESTUS_MANAGED_CHROMIUM_PATH` 为服务端可执行的 Chromium/Chrome 路径；Cookie 导入模式不需要启动 Playwright Worker。然后运行：

macOS 常见路径是 `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`，Linux 常见路径是 `/usr/bin/google-chrome` 或 `/usr/bin/chromium`；路径必须是运行 FastAPI 进程的那台机器上的可执行文件。

```bash
python3 scripts/init_db.py
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

进入 `/admin` 后按以下顺序操作：

1. 在“平台管理”创建方舟入口，入口 URL 填实际业务首页或工作台地址。
2. 打开“桌面用户”，点击目标用户后的“绑定托管账号”，选择“账号密码”或“Cookie”，填写对应凭据；业务平台固定为方舟，不设置到期日。
3. 每个用户只保留一个方舟托管账号，重新保存即覆盖；Cookie 直接粘贴完整 JSON。
4. 启动桌面端、登录对应桌面用户、同步配置，再点击方舟平台入口。托管启动顺序是 `about:blank → Rust 注入 Cookie → 导航到业务 URL`。

本地验收重点：重复点击平台按钮只激活已有平台页；轮换凭据后旧版本 profile 会关闭；解绑、撤销、平台停用或账号过期后，旧的一次性票据不能继续兑换；验证码/MFA 时客户机不会退回方舟登录页。验证过程中可以运行现有测试：

```bash
python3 -m pytest -q
cargo test --manifest-path desktop/src-tauri/Cargo.toml --all-targets
cd web && npm test && npm run build
```

本地 Chromium 模式只能隐藏正常界面，不能阻止客户通过本机 profile、进程、DevTools 或修改客户端取得 Cookie、退出或换号；若验收标准要求这些行为在客户完全控制本机时仍不可行，需要按本文远程浏览器方案继续实现。

## 1. 结论先行

这个需求可以分成两个安全等级：

| 目标 | 本地受控 Chromium | 服务端远程浏览器 |
| --- | --- | --- |
| 客户不需要手动登录 | 可以 | 可以 |
| 客户界面不显示方舟密码 | 可以 | 可以 |
| Vestus 按钮不主动新开标签 | 可以 | 可以 |
| 客户无法从本机取得 Cookie | 做不到 | 可以做到 |
| 客户无法故意退出或切换方舟账号 | 只能做软限制 | 可以由服务端统一控制 |

建议先把产品流程改成“托管登录模式”，默认优先使用短期 Cookie/会话。账号密码只留在后台或服务端 Worker，不直接下发到 React，也不让客户填写。若“客户本机即使有技术能力也不能取得会话”是硬要求，则最终应使用服务端远程浏览器；本地注入方案不能作出这个保证。

本方案不修改 Vestus 自身登录页的“记住登录信息”行为。Vestus 客户端密码和方舟业务账号是两套凭据，必须分开管理。

管理后台的使用者可以只填写方舟账号和密码；密码由后台保存并交给服务端登录 Worker 使用。客户桌面端只拿到托管会话，不拿到方舟原始密码。若连 Vestus 客户端账号密码也不允许客户知道，则需要另做设备授权登录，本方案不覆盖这一点。

## 2. 当前代码与缺口

当前 `Platform` 只有名称、网址、图标、排序和状态，没有方舟账号、密码或 Cookie 字段：[app/db/models/platform.py](../../app/db/models/platform.py:14)。

桌面配置接口目前只返回代理、平台入口、`profileKey` 和租约：[app/services/desktop.py](../../app/services/desktop.py:50)；桌面端的 `DesktopConfigWire` 也没有托管登录字段：[desktop/src-tauri/src/commands.rs](../../desktop/src-tauri/src/commands.rs:67)。

改造前打开平台时，Chromium 会把平台 URL 作为启动地址，找不到页面时还会创建新 target，CDP 失败时通过 `--new-window` 兜底。当前本地实现已删除这两个入口，重复点击只激活已有平台页：[desktop/src-tauri/src/commands.rs](../../desktop/src-tauri/src/commands.rs:654)。

当前 CDP 采集通道仍然只读；托管登录使用独立的 `managed_cdp.rs` 控制模块，静态检查继续禁止采集通道获得写入能力：[desktop/src-tauri/src/managed_cdp.rs](../../desktop/src-tauri/src/managed_cdp.rs:1)、[desktop/scripts/check-surface-boundaries.mjs](../../desktop/scripts/check-surface-boundaries.mjs:51)。

现有浏览器 profile 会落在客户机上，项目也明确记录了同一操作系统用户的其他进程可以读取 profile 和本地 DevTools 端点：[desktop/src-tauri/src/browser.rs](../../desktop/src-tauri/src/browser.rs:28)。这就是本地方案无法保证 Cookie 绝对保密的原因。

## 3. 目标和非目标

### 目标

1. 客户点击“巨量/方舟”后直接看到业务首页或工作台，不出现登录表单。
2. 客户不输入、看不到方舟账号密码。
3. 方舟凭据不进入 React、普通浏览器页面脚本、活动日志、错误提示或 `desktop-config` 的通用响应。
4. 每个 Vestus 用户只能拿到后台为其绑定的方舟账号会话。
5. 点击平台入口不会因为重复点击而创建第二个受控平台标签。
6. 会话过期、被后台撤销或配置版本变化时，浏览器关闭并提示联系管理员，不能退回手动登录流程。
7. 管理员可以轮换、撤销和审计托管账号。

### 非目标

1. 不修改 Vestus 客户端账号的登录和“记住登录信息”功能。
2. 不把方舟账号密码写入客户端 localStorage、配置文件或活动采集队列。
3. 不把“隐藏按钮”当成强安全边界。客户完全控制本机时，本地方案无法阻止其读取进程、profile 或修改客户端。
4. 不逆向或绕过方舟验证码、风控和设备绑定。需要使用方舟允许的账号、SSO、授权或合法浏览器会话。

## 4. 推荐方案：托管 Cookie，会话按客户绑定

### 4.1 凭据原则

优先级如下：

1. 方舟官方 SSO/OAuth/子账号授权；
2. 服务端 Worker 使用后台保存的账号完成登录，向桌面端发放短期会话包；
3. 管理员导入短期 Cookie 包；
4. 直接把账号密码发到客户机并自动填充，仅作为最后的兼容方案，不作为默认方案。

直接下发密码的问题是：即使密码只进入 Rust，客户仍可在本机调试客户端或观察进程。直接把 Cookie 发到本机则是把等价的 Bearer 凭证发给客户机。两者都只能做到“正常界面不显示”，不能做到“客户技术上无法取得”。

Cookie 包需要保存完整属性，而不是只保存 `name=value`：`domain`、`path`、`secure`、`httpOnly`、`sameSite`、过期时间和版本。方舟会话可能绑定 IP、设备、User-Agent 或风控状态，不能假设一份 Cookie 可以长期跨机器复用。

### 4.2 数据模型

不要把业务账号直接加到全局 `platform` 表。建议新增独立模块：

`managed_platform_account`

- `id`
- `platform_id`
- `name`：管理员看到的别名，不是方舟密码
- `auth_mode`：`cookie`、`server_login`、`official_sso`
- `encrypted_username`：仅在需要时保存
- `encrypted_password`：仅后台/Worker 使用，使用独立密钥
- `encrypted_cookie_bundle`
- `credential_version`
- `expires_at`
- `status`：`active`、`expired`、`revoked`、`invalid`
- `last_verified_at`
- `created_at`、`updated_at`

`user_platform_managed_binding`

- `user_id`
- `platform_id`
- `managed_account_id`
- `status`
- `updated_at`

`managed_browser_session`

- `id`
- `user_id`
- `platform_id`
- `device_id`
- `credential_version`
- `browser_mode`：`local` 或 `remote`
- `lease_hash`
- `started_at`、`last_seen_at`
- `revoked_at`

托管 profile 的派生键必须包含 `managed_account_id` 和 `credential_version`，并固定代理/直连模式；管理员替换用户的方舟凭据时，不能复用旧版本 profile。需要删除或隔离旧 profile 中的 Cookie、Local Storage、Service Worker 和缓存，避免账号混合。

新配置的方舟账号密码和 Cookie 按产品要求明文保存，仅超级管理员管理接口返回；旧版本密文仍使用独立的 `VESTUS_PLATFORM_SECRET_KEY` 兼容读取。日志只记录用户、版本和结果，不记录密码、Cookie 值、完整请求体或完整 Cookie 头。

### 4.3 后台接口

托管凭据不要放进通用 `desktop-config`，而是在客户点击平台后按需申请：

`POST /api/user/managed-platforms/{platform_id}/bootstrap`

服务端校验：

- Vestus 用户仍然有效；
- 用户确实绑定了该平台和托管账号；
- 设备 ID、客户端版本和账号状态符合要求；
- 托管账号未过期或撤销；
- 当前凭据版本与租约一致。

响应只用于 Rust 内存中的一次启动流程，设置 `Cache-Control: no-store`，并带一次性短 TTL。React 不调用这个接口，也不接触响应内容。

推荐响应结构：

```json
{
  "sessionId": "one-time-id",
  "credentialVersion": 7,
  "cookieBundle": [
    {
      "name": "...",
      "value": "...",
      "domain": ".oceanengine.com",
      "path": "/",
      "secure": true,
      "httpOnly": true,
      "sameSite": "Lax",
      "expiresAt": "2026-11-02T12:00:00Z"
    }
  ],
  "allowedHosts": [
    "agent.oceanengine.com",
    "sso.oceanengine.com",
    ".oceanengine.com"
  ],
  "expiresAt": "2026-11-02T12:10:00Z"
}
```

实际实现中应优先使用一次性会话票据，再由 Rust 兑换会话包；原始密码不返回给桌面端。可以增加 Rust 临时公钥加密响应，防止同机中间层或错误日志泄露，但这不能防止客户调试自己的 Rust 进程。

示例中的域名只是说明格式，不是可直接上线的白名单。当前观测还出现过 `ttwid.bytedance.com`、`localads.chengzijianzhan.cn`、`lf3-ad-platform.byteadverts.com` 和 `lf-ucenter-web.yhgfb-cn-static.com`。后台必须按平台真实登录链路维护精确 allowlist，Rust 只接受服务端签发且与平台配置版本匹配的域名，不能让客户端自行扩大 Cookie domain 或允许域名。

bootstrap 票据必须由服务端原子消费，并绑定 Vestus 用户、设备、平台、凭据版本和用途；重复兑换直接失败。短 TTL 只保护“取包接口”，不会缩短已经注入浏览器的 Cookie 有效期。

### 4.4 桌面端启动流程

```text
客户点击“巨量/方舟”
        │
        ▼
Rust 校验 Vestus 登录、平台绑定、租约和本机设备
        │
        ▼
申请一次性托管会话包
        │
        ▼
以 about:blank 启动该平台的独立 Chromium profile
        │
        ▼
取得 CDP endpoint
        │
        ▼
通过独立 ManagedBrowserControl 注入 Cookie
        │
        ▼
创建唯一平台 target，导航到业务入口
        │
        ▼
确认未跳转到登录页，并启动只读活动采集
        │
        ▼
客户直接使用已登录的方舟页面
```

必须先用 `about:blank` 启动，再注入 Cookie，最后导航到方舟入口，避免首个请求在未认证状态下触发方舟风控或显示登录页。

Cookie 注入代码必须与现有只读采集代码分开，例如当前的 `managed_cdp.rs`。该模块只允许固定的 `Network.setCookies`、target attach、导航和 detach 命令，并配套单测和静态检查；不能因为增加托管登录而让通用活动采集获得任意 `Runtime.evaluate`、页面脚本执行或读取 Cookie 的能力。

如果会话验证失败：

- 关闭当前受控浏览器；
- 删除或隔离当前托管 profile；
- 返回“托管登录已失效，请联系管理员”；
- 不显示方舟登录页；
- 不提供客户输入方舟账号密码的入口。

### 4.5 不主动新开标签

当前实现已经完成以下改造：

1. 首次启动时创建唯一的受控 target。
2. 后续点击只激活该 target。
3. 删除找不到页面时的 `Target.createTarget` fallback。
4. 删除 CDP 失败时的 `--new-window` handoff fallback。
5. 找不到唯一 target 时返回明确错误，要求重新初始化托管会话。
6. 前端去掉 `created`、`window` 等成功提示，只保留“已激活已有平台页”。

这能保证“客户点击 Vestus 的平台按钮”不会主动开第二个页面。它不能限制客户在普通 Chromium 窗口里手动使用 `Ctrl+N`、`Ctrl+L` 或浏览器菜单。

## 5. 方舟登录页和退出行为

下一阶段可以增加导航监测：

- 发现目标跳转到方舟登录页、注册页或账号切换页，立即关闭该 target；
- 发现不在 `allowedHosts` 的目标，关闭 target 或整个托管浏览器；
- 后台租约撤销时关闭整个浏览器；
- 会话失效时重新申请托管会话，不显示人工登录入口。

这仍然是客户端软限制。客户拥有本机权限时，可以修改客户端、绕过监测或直接操作浏览器 profile。方舟的退出请求、SSO 跳转和 Cookie 刷新路径也可能变化，不能把 URL 拦截当成长期强安全方案。

外置 Chromium 的本地模式无法保证登录页在任何竞态下都完全不闪现；如果产品验收要求“登录页绝不出现在客户屏幕上”，必须使用服务端远程浏览器，或者改成具备导航策略接口的嵌入式浏览器，并在导航提交前拒绝登录域名。

如果必须可靠禁止退出和换号，浏览器应运行在服务端 Worker：

```text
后台托管方舟账号/Cookie
        │
        ▼
服务端 Worker 中的 Chromium profile
        │ 服务器控制导航、Cookie、网络和 target
        ▼
WebRTC/VNC/受控输入流
        │
        ▼
客户桌面端只显示画面并转发操作
```

远程模式下方舟 Cookie 不进入客户机，服务端可以阻止登录页、退出接口、新 target 和非允许域名，并在管理员撤销后立即关闭会话。Worker 还必须使用与账号验证一致的代理出口、浏览器版本、User-Agent 和 profile 策略，否则方舟可能因 IP/设备/UA 变化使会话失效。代价是新增 Worker 调度、画面流、输入转发、并发控制和运维体系。

## 6. 管理后台设计

管理后台不再提供独立托管账号菜单。超级管理员在每个桌面用户行后点击“绑定托管账号”，只选择认证方式并填写账号密码或 Cookie；平台固定为方舟，不设置到期日。已保存的明文密码和 Cookie 只在超级管理员的用户配置弹窗中回显，输入和覆盖动作写入审计日志。

建议审计事件：

- `MANAGED_ACCOUNT_CREATED`
- `MANAGED_ACCOUNT_ROTATED`
- `MANAGED_ACCOUNT_REVOKED`
- `MANAGED_SESSION_BOOTSTRAP_ISSUED`
- `MANAGED_BROWSER_STARTED`
- `MANAGED_BROWSER_AUTH_FAILED`
- `MANAGED_BROWSER_REVOKED`

## 7. 管理员只输入账号密码，系统自动取得 Cookie

### 7.1 推荐流程

```text
超级管理员在用户行内填写方舟账号和密码
        │ HTTPS
        ▼
后端明文保存密码，仅超级管理员可读取
        │
        ▼
服务端登录 Worker 启动独立 Chromium profile
        │
        ▼
Worker 打开方舟登录页，填写账号密码并完成 SSO 跳转
        │
        ├─ 无验证码/二次验证：自动完成
        └─ 有验证码/二次验证：状态变为 needs_manual_verification
        │
        ▼
Worker 验证已登录并提取完整 Cookie 属性
        │
        ▼
Cookie 明文保存，后台仅向超级管理员回显
```

当前实现由 FastAPI 请求内的 Playwright provider 启动无头 Chromium，完成一次验证后把 Cookie 加密保存；它已经能支持“管理员只输入账号密码”，但还不是带队列、独立 profile 和重试策略的常驻 Worker。生产环境建议把这段 provider 拆成独立 Worker，避免登录、验证码和浏览器进程占用 API 请求进程。

Worker 应使用真实 Chromium 浏览器上下文，而不是直接拼方舟登录 HTTP 请求。方舟登录链路包含 SSO 跳转、CSRF、设备指纹和可能的风控参数；仓库的历史观测记录了 `/passport/sso/account_login/v2/`、登录回调和 `/ttwid/check/`，这说明简单的“后台 POST 用户名密码”不能作为已验证方案。[ttwid 实测记录](../../js_reverse_cache/ttwid-investigation/findings-20260924.md)

管理员遇到验证码或二次验证时，后台不应把登录页转给客户。应显示 `needs_manual_verification`，由管理员在受控的后台 Worker 会话中完成一次验证；成功后 Worker 再保存会话。若方舟不允许服务端登录或要求强设备绑定，应改用官方 SSO/授权，不能绕过风控。

### 7.2 两种会话交付方式

| 模式 | Cookie 所在位置 | 客户端拿到的内容 | 适用场景 |
| --- | --- | --- | --- |
| 本地托管模式 | 客户机 Rust/Chromium profile | Cookie 会话包 | 先满足“点击即登录”的体验；不能防本机提取 |
| 远程浏览器模式 | 服务端 Worker profile | 远程会话票据和画面流 | 需要客户无法取得 Cookie |

本地模式必须明确承认：Worker 自动取得 Cookie 后，Cookie 最终仍会进入客户机浏览器。远程模式则只把画面和受控输入发给客户，Cookie 不离开 Worker。

## 8. Cookie 时效与自动更新

目前不能给出一个可信的“固定有效 X 天”。仓库已有观测只证明了环境 Cookie 的行为：`ttwid` 曾返回 `max-age=31536000`，但在登录前的 `/ttwid/check/` 又被刷新。它不是方舟账号登录 Cookie 的有效期，不能按一年配置登录续期。

实际策略应同时记录三种状态：

1. Cookie 属性中的 `expires` 或 `max-age`；
2. Worker 最近一次验证成功时间；
3. 受控业务探针的实时结果，例如方舟登录状态检查或一个无副作用的已登录页面请求。

建议先采用以下保守策略，待真实账号测试后再调整：

- Worker/客户端活跃期间每 5 分钟做一次轻量会话探测；
- 有明确过期时间时，在 `expires - 10 分钟` 进入续期；
- 没有明确过期时间或服务端提前失效时，以探针失败为准立即重新登录；
- 续期失败不显示方舟登录页，关闭托管浏览器并提示管理员处理；
- 每次成功重新登录都递增 `credential_version`，旧会话租约立即失效。

这里的“bootstrap 短 TTL”只限制一次性取包接口，不会自动缩短已经注入浏览器的方舟 Cookie 寿命。若本地模式的 Cookie 被客户导出，其可复用时间仍由方舟服务端、Cookie 属性和风控决定；要让凭据不落客户机，只能使用远程浏览器。

必须用真实账号做 TTL 实验：

| 实验 | 记录内容 |
| --- | --- |
| 登录成功时 | 每个 Cookie 的域、路径、过期时间和属性；值只存摘要 |
| 每 5 分钟探测 | HTTP 状态、是否重定向登录页、Cookie 是否被 Set-Cookie 刷新 |
| 正常关闭后重开 | 会话是否仍有效 |
| 代理/IP 不变与变化 | 是否触发重新验证或风控 |
| 退出、改密、管理员撤销 | 原会话何时失效 |
| 至少 3 个账号、持续 24–72 小时 | 最短有效时间、平均有效时间、提前失效原因 |

实验结束后，把策略设置为“明确 Cookie 过期时间减安全余量”和“探针失败立即重建”两者中更早者，而不是写死 7 天、30 天或 1 年。

## 9. 失效、轮换和恢复

| 场景 | 客户端行为 | 管理员行为 |
| --- | --- | --- |
| Cookie 即将过期 | 在浏览器关闭后重新申请，不显示登录页 | 更新 Cookie 或服务端登录会话 |
| Cookie 已失效 | 关闭浏览器并提示联系管理员 | 重新验证或轮换凭据 |
| 管理员撤销 | 下一个租约心跳内关闭浏览器 | 可查看撤销审计 |
| 平台配置变化 | 关闭旧会话，按新版本重新初始化 | 更新平台域名/允许域名 |
| 设备变化 | 拒绝兑换或要求新设备授权 | 管理员批准新设备 |
| 方舟风控/验证码 | 标记 `auth_failed`，不让客户手动登录 | 在服务端 Worker 或管理员流程处理 |

## 10. 实施顺序

### 阶段 A：本地托管 Cookie（体验版，核心链路已实现）

1. 新增托管账号和用户绑定表、迁移；旧密文保留兼容读取，新配置按要求明文保存。
2. 增加服务端 Playwright provider，完成账号密码登录、验证和 Cookie 提取；常驻 Worker 化仍属于生产加固项。
3. 在桌面用户列表增加超级管理员专用的托管账号配置弹窗，删除独立菜单。
4. 增加按平台申请一次性托管会话的后端接口。
5. Rust 增加独立的托管会话模块和 Cookie 注入流程。
6. 平台首次启动改为 `about:blank → 注入 → 业务入口`。
7. 删除 Vestus 平台按钮的 `createTarget` 和 `--new-window` fallback。
8. 失效时关闭浏览器，不显示方舟登录页。
9. 托管模式固定使用管理员配置的代理线路；“切换直连”和“重置本机浏览器环境”仍是本地软限制，后续可改成管理员授权操作。
10. 保留 Vestus 自身“记住登录信息”逻辑，不改 `LoginCard.tsx`。

### 阶段 B：本地软限制和验收

1. 增加允许域名和登录页导航监测。
2. 增加托管会话 lease 心跳和撤销关闭。
3. 增加真实方舟账号的 Cookie 过期、刷新、IP/设备变化测试。
4. 验证 React、活动日志和错误提示中没有凭据。
5. 明确对外说明：本地模式不能抵抗客户本机调试、读 profile 或改包。

### 阶段 C：远程浏览器（强安全版）

1. 新增服务端 Worker 和每个托管账号独立 profile。
2. 增加画面流和输入转发协议。
3. 服务端实现 target、域名、退出和会话租约控制。
4. 客户端改为显示远程会话，不保存方舟 Cookie。
5. 以服务端撤销、退出、切号和凭据不可达作为最终验收标准。

## 11. 验收标准

### 本地体验版必须满足

- 点击巨量后不出现方舟登录表单，直接进入业务页面或明确失败。
- 方舟账号密码不经过 React，不进入日志和活动采集。
- 重复点击平台按钮不创建第二个受控 target。
- Cookie 失效时不允许客户自行输入另一个账号。
- 管理员撤销后浏览器按租约关闭。
- Vestus 登录页原有“记住登录信息”行为不改变。
- 管理员只需输入方舟账号密码，后台能显示验证结果；密码不回显给其他角色，Cookie 值不进入日志。
- Cookie 失效或需要验证码时，进入管理员处理状态，不把方舟登录页交给客户。

### 强安全版必须额外满足

- 客户机进程、文件和网络包中没有方舟 Cookie 或密码。
- 客户无法打开方舟登录页、退出接口或第二个 target。
- 方舟会话只存在远程 Worker。
- 管理员撤销后远程会话立即失效。

## 12. 最终建议

如果老板当前要的是“客户点击后直接进入已登录状态，客户平时不接触方舟密码”，先实施阶段 A 和 B，优先使用 Cookie/服务端登录，不把密码发到客户机。

如果老板说的“禁止退出和换号”包括客户有意调试本机、复制 Cookie 或修改客户端后也不能绕过，那么阶段 A 不够，应该直接按阶段 C 规划远程浏览器，并把本地模式仅作为过渡方案。
